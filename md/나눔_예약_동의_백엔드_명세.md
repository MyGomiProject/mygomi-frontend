# 나눔 게시글 예약 동의 API 명세 (백엔드)

프론트엔드에서 **채팅방 내 "예약하기"** 기능을 구현하기 위해 필요한 백엔드 API 및 동작 방식입니다.  
**글 작성자**와 **채팅 상대(나눔 신청자)** 둘 다 "예약"을 눌렀을 때만 게시글 상태가 `RESERVED`로 변경되어야 합니다.

---

## 1. 비즈니스 규칙

| 항목 | 설명 |
|------|------|
| 참여자 | 게시글 작성자(Author), 나눔 신청자(Requester) — 채팅방은 이 둘만 존재한다고 가정 |
| 예약 확정 조건 | **두 명 모두** "예약 동의"를 한 경우에만 해당 게시글의 `status`를 `RESERVED`로 변경 |
| 이미 예약됨 | 게시글 `status`가 이미 `RESERVED` 또는 `COMPLETED`, `DELETED`인 경우 "예약 동의" 불가 또는 무시 |

---

## 2. 필요한 REST API

### 2.1 예약 상태 조회

**목적**: 채팅방 진입 시 "내가 이미 동의했는지", "상대가 동의했는지", "게시글 현재 상태"를 보여주기 위함.

| 항목 | 내용 |
|------|------|
| Method | `GET` |
| URL | `GET /api/share-posts/{postId}/reservation/status` |
| 인증 | 필요 (Bearer Token) |
| 설명 | 해당 게시글에 대한 "예약 동의" 상태를 반환 |

**응답 예시 (200 OK)**

```json
{
  "data": {
    "postId": 12,
    "postStatus": "OPEN",
    "myAgreed": true,
    "otherAgreed": false,
    "bothAgreed": false
  },
  "meta": {
    "timestamp": "2026-02-22T12:00:00"
  }
}
```

| 필드 | 타입 | 설명 |
|------|------|------|
| postId | number | 게시글 ID |
| postStatus | string | 게시글 현재 상태: `OPEN`, `RESERVED`, `COMPLETED`, `DELETED` |
| myAgreed | boolean | 현재 로그인 사용자가 "예약 동의"를 눌렀는지 |
| otherAgreed | boolean | 채팅 상대가 "예약 동의"를 눌렀는지 (프론트에서 "상대방 수락 대기 중" 등 표시용) |
| bothAgreed | boolean | 두 명 모두 동의했는지 (이미 확정된 경우 true, 이때 postStatus는 RESERVED 등) |

- **채팅 상대** 정의: 해당 게시글의 작성자 userId와 요청자 userId를 비교해, 요청자 입장에서는 "작성자"가 other, 작성자 입장에서는 "해당 글에 대해 채팅한 상대(첫 번째 신청자 등)"가 other로 정의되면 됨.  
  (실제 구현은 백엔드에서 채팅방/대화 상대 개념으로 정하면 됨.)

---

### 2.2 예약 동의 하기

**목적**: 사용자가 "예약하기" 버튼을 눌렀을 때 호출. 서버에서 동의 상태를 저장하고, **이미 상대도 동의한 상태라면** 게시글 상태를 `RESERVED`로 변경.

| 항목 | 내용 |
|------|------|
| Method | `POST` |
| URL | `POST /api/share-posts/{postId}/reservation/agree` |
| 인증 | 필요 (Bearer Token) |
| Request Body | 없음 또는 `{}` |
| 설명 | 현재 사용자가 해당 게시글에 대해 "예약 동의"함. 두 명 모두 동의한 경우 게시글 상태를 RESERVED로 변경. |

**응답 예시 (200 OK)**

```json
{
  "data": {
    "postId": 12,
    "postStatus": "RESERVED",
    "myAgreed": true,
    "otherAgreed": true,
    "bothAgreed": true
  },
  "meta": {
    "timestamp": "2026-02-22T12:00:00"
  }
}
```

- **동작**  
  - 게시글이 `OPEN`이 아니면: 400 등으로 실패 처리 권장.  
  - 이미 본인이 동의한 경우: 200으로 기존 상태 그대로 반환해도 됨.  
  - 본인 동의 저장 후, 상대도 이미 동의한 상태면 `postStatus`를 `RESERVED`로 변경 후 위와 같이 반환.

---

## 3. 에러 응답

| HTTP 상태 | 상황 예시 |
|-----------|-----------|
| 400 | 게시글이 OPEN이 아님(이미 RESERVED/COMPLETED/DELETED) |
| 401 | 미인증 |
| 403 | 해당 게시글 채팅 상대가 아님(예약 동의 권한 없음) |
| 404 | postId에 해당하는 게시글 없음 |

---

## 4. 데이터 모델 제안 (백엔드)

예약 동의 상태를 저장하기 위한 테이블(또는 기존 테이블 확장) 예시입니다.

**예: `share_post_reservation_agreement`**

| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | PK | |
| share_post_id | FK | 게시글 ID |
| user_id | FK | 동의한 사용자 ID (작성자 또는 신청자) |
| agreed_at | timestamp | 동의 시각 |

- Unique 제약: `(share_post_id, user_id)` — 한 사용자가 같은 글에 대해 한 번만 동의.
- 두 명 모두 레코드가 있으면 `post.status`를 `RESERVED`로 업데이트.

또는 게시글·채팅방 구조에 맞게 **채팅방(room) 단위**로 예약 동의를 관리해도 됩니다.  
(예: `chat_room_id` + `user_id`로 동의 여부 저장 후, 해당 room의 post_id에 대해 두 명 모두 동의 시 post status 변경.)

---

## 5. (선택) WebSocket으로 실시간 반영

REST만으로도 동작 가능합니다.  
다만 **상대가 예약 동의했을 때** 화면을 바로 갱신하려면 WebSocket(또는 SSE)을 사용할 수 있습니다.

- **구독**  
  - 채팅방/게시글 단위 구독 경로 예: `/topic/share-posts/{postId}/reservation`
- **이벤트**  
  - 상대가 "예약 동의"했을 때 서버에서 해당 토픽으로 메시지 발행  
  - payload 예: `{ "postId": 12, "postStatus": "RESERVED", "bothAgreed": true }`
- **프론트**  
  - 해당 메시지 수신 시 예약 상태 조회 API 재호출 또는 payload로 로컬 상태 갱신 후 "예약 확정됨" 등 표시

WebSocket 미구현 시에는 REST만 사용하고, 사용자가 채팅방을 다시 열거나 "예약하기" 버튼을 누른 뒤 응답으로 상태를 갱신해도 됩니다.

---

## 6. 프론트엔드 연동 요약

- 채팅방 오픈 시: `GET /api/share-posts/{postId}/reservation/status` 호출 후  
  - `myAgreed` / `otherAgreed` / `postStatus`에 따라  
  - "예약하기" / "예약 요청함" / "상대방 수락 대기 중" / "예약 확정됨" 등 문구 표시.
- "예약하기" 클릭 시: `POST /api/share-posts/{postId}/reservation/agree` 호출 후  
  - 응답의 `postStatus`, `bothAgreed`로 UI 갱신 및 필요 시 게시글 목록 캐시 무효화.

이 명세대로 구현해 주시면, 프론트엔드 채팅방 예약 버튼과 연동할 수 있습니다.
